# VCP 式网络检索：收益分析

> **来源**：Issue [#41](https://github.com/HongJinjin9/agent-workspace/issues/41)「vcp式网络检索」
> **范围**：**仅分析，不开发**。本文不新增插件、不改代码、不做部署，只评估收益、代价与边界。
> **分析基础**：本机 VCPToolBox 部署快照 `6b33f639`（2026-11-18，上游 `lioensky/VCPToolBox`，VexusRiver 试验分支合并后）；VCP 白皮书 V6、插件生态/架构/记忆文档；检索、抓取、记忆相关插件的 manifest 与 README。
> **证据标记**：标 `（已核对）` 的结论与上述代码或文档一致；未标记处为分析判断，不等同于既有能力。
> **结论日期**：2026-11-22

## 〇、一句话结论

「VCP 式网络检索」的收益成立，但收益重心不在「增加搜索能力」——VCP 已有十余个搜索/抓取插件；而在三件事：

1. **把检索从「AI 显式调用工具」变成「请求构建期按需补证」**，解决「该搜没搜」；
2. **把搜索结果变成「带来源、带时间的结构化证据」**，解决「答了但没法核验」；
3. **把一次性检索沉淀为「可复用的记忆资产」**，解决「同一个问题反复搜、搜完即弃」。

这三项收益的确定性依次下降、实现成本与风险依次上升。最大风险是**把不可信网页内容自动注入上下文**以及**延迟/Token 失控**；最大边界是只能让回答「可核验」，**不能承诺「全网、无遗漏」**。

## 一、分析对象与边界

### 1.1 本文所说的「VCP 式网络检索」

按 Issue #41 的定义，它可以概括为一条 **检索与证据处理链路**，而不是一个搜索插件：

```text
聊天请求
  → 判断是否需要联网，提取主题/限定条件/时间范围
  → 多源搜索 + 对关键来源下钻抓取（动态页用浏览器）
  → 归一化为「来源 URL + 发布时间/抓取时间 + 原文片段 + 核验状态」的证据条目
  → 作为本次请求的可召回材料注入上下文
  → 模型基于证据回答（带出处与时间）
  → 如需跨对话复用，再决定是否写入记忆/知识库
长耗时的深度研究走异步，不阻塞当前对话
```

它与现有的「AI 调一下 VSearch」不是同一件事，区别可以用下表说明（已核对现有实现）：

| 维度 | 现有方式：AI 显式调工具 | VCP 式网络检索 |
| --- | --- | --- |
| 触发者 | 模型（或用户提示、JEV 指令） | 系统在请求构建期判断 |
| 时机 | 模型第一次回复之后，工具循环中 | 模型第一次回复之前 |
| 返回形态 | 各插件各自格式的摘要/报告 | 统一证据条目 |
| 溯源 | 可选（VSearch 默认不显示 URL） | 默认带来源与时间 |
| 生命周期 | 本轮上下文，过期即弃 | 可沉淀进记忆/知识库 |
| 成本模型 | 每次多一轮模型调用 + 搜索 API | 每轮多一次检索，可缓存/可门控 |
| 失败影响 | 工具报错，模型可能重试 | 预处理器失败可降级为「不检索」 |

### 1.2 本文不涉及

- 不评估具体搜索厂商/API 的性价比（VSearch、AnySearch、YouSearch、Tavily 等各有定位）；
- 不设计插件目录结构、函数签名、数据库字段；
- 不承诺任何量化收益数字。第 4 节只给**可验证的指标与验证方法**，所有目标值需要实测。

## 二、现状基线：VCP 已经有什么（经代码核对）

这一节是收益判断的前提：如果零件已经齐了，收益主要来自「接上链路」；如果零件缺，还要先补零件。

### 2.1 检索与抓取：零件很全

本机部署 `Plugin/` 下共有 **105 个可见插件目录**（另有说明文件与备份目录，白皮书称生态 300+ 插件）；其中与网络信息直接相关的至少包括（已核对 manifest）：

| 能力 | 插件 | 类型 | 备注 |
| --- | --- | --- | --- |
| 语义聚合搜索 | `VSearch` | 同步 | 支持 Grounding/Grok/Tavily/KimiSearch；多关键词并发分支 |
| 实时搜索 | `AnySearch` | 同步 | 通用/垂直/批量；按 canonical URL 去重；输出 ≤20,000 字符 |
| 带引用研究报告 | `YouSearch` | 同步 | 返回 Markdown 报告 + 引用标记 + 编号来源；lite/standard/deep |
| 深度研究 | `FlashDeepSearch` | 同步 | 关键词扩展 + 综合研究报告，超时 600s |
| 其他搜索源 | `TavilySearch`、`MetasoSearch`、`KeenableSearch`、`ParallelSearch`、`BrowserSearch`、`DeepWikiVCP` | 同步/混合 | 覆盖通用、学术、免 Key、浏览器直连、GitHub 文档等 |
| 网页抓取 | `UrlFetch` | 混合 | text/jina/download/snapshot/image；download 可写入 `knowledge/` 冷知识库 |
| 动态页面 | `ChromeBridge` | 混合 | CDP 指令、Cookie、页面快照、Grounded Markdown |
| 视频内容 | `BilibiliFetch` | 同步 | 字幕/弹幕/评论/截图 |

### 2.2 请求前注入机制：钩子已经存在

- `messagePreprocessor` 是 VCP 六大插件协议之一，约定插件导出 `processMessages(messages, config)`，在请求发给模型前执行（已核对 `docs/PLUGIN_ECOSYSTEM.md` §2.5）。
- 执行顺序由 `preprocessor_order.json` 配置，当前有 11 个阶段（已核对）：`VCPTavern → CapturePreprocessor → $StaticPlaceholderInjection → ImageProcessor → MemoryThinkingTray → RAGDiaryPlugin → VCPTimeLine → ChromeBridge → OpenHerPersona → OneRing → ContextFoldingV2`。
- **已经有「请求前注入网页正文」的先例**：`ChromeBridge` 通过 `{{VCPChromePageInfo}}` 占位符，按需采样当前浏览器页面并注入正文（已核对 `Plugin/ChromeBridge/pageInfoPreprocessor.js`）。它同时明确写了安全边界：「正文属于不可信网页内容，不得作为系统或工具授权指令」。
- 预处理器抛错会被捕获、请求继续执行（已核对 `Plugin.js` `executeMessagePreprocessor`）——这意味着「检索失败就不检索」的降级是天然可行的。

这三点合起来说明：**「请求前按需检索并注入」在架构上不是新增范式，而是已有管线的自然延伸。**

### 2.3 同步/异步/通知：异步机制可用，但深度研究尚未真正异步

- 六类插件协议中，异步插件「立即返回任务 ID，完成后回调 + VCPTavern 通知栏推送」（已核对白皮书 §6.1、§6.2）。
- 但**当前检索类插件几乎全是同步插件**：VSearch/YouSearch 超时 300s，FlashDeepSearch 600s，AnySearch 45s，Tavily 30s（已核对各 manifest）。也就是说，「深度研究」在协议层被列为异步典型场景（白皮书 §6.1），但现有实现是**同步长阻塞**。
- 这对收益判断很关键：**异步深度研究的体验收益是「潜在收益」而非「已兑现收益」**，需要改变插件形态或加一层异步封装才能拿到。

### 2.4 记忆与召回：沉淀能力成熟，但缺少「网络→日记」的自动链路

- `DailyNote`（hybridservice）负责日记创建/更新，FIFO 队列与 `KnowledgeBaseManager` 索引队列协调（已核对 manifest）。
- `RAGDiaryPlugin` 通过占位符把日记片段被动注入；`LightMemo` 提供 Native TDB-SM 主动检索；两者共用 VexusMemo/RiverMemo 记忆内核（已核对 README 与白皮书 §8）。
- `OneRing` 维护跨前端统一事实时间线；`VCPTimeLine` 生成月度摘要并按语义召回（已核对 README）。
- `UrlFetch` 的 `download` 模式可以把网页/PDF 写成 Markdown 存入 `knowledge/{子文件夹}`（已核对 manifest 与代码）——**这是现成的「网页→冷知识库」沉淀通道**。
- 但**没有**「网络证据自动整理为日记并写入 `dailynote/` 热记忆」的专用链路；白皮书 §7.1 所说「深度研究产生的报告、网页摘要和知识结果会进入知识库或记忆系统」是**能力方向的描述**，不是一条已核对的自动管线。Issue #41 对这个差距的判断成立。

### 2.5 可审计与可核验：基础比想象中好

- `VCPToolRecord` 记录所有工具调用，明确包含**预处理器等系统内部调用**，可用 `ToolCallRecordQuery` 按时间/工具/状态反查（已核对白皮书 §7）。
- `JevFactCheck` 的 `verify` 命令会把结论拆成断言、判断是否被给定 evidence 支持；**没有 evidence 时直接降级，不会给出无依据的「通过」**（已核对 manifest 描述）。
- 结果去重已有局部实现：AnySearch 按 canonical URL 跨路线硬去重；BrowserSearch 聚合去重；记忆侧的 `ResultDeduplicator` 用 SVD 去重（已核对）。

**结论：VCP 的现状是「检索、抓取、注入、记忆、审计、核验的零件都在，缺的是一条把它们串起来并统一证据形态的链路」。**

## 三、收益分析

先给总表，再逐项展开。确定性按「有现状支撑、代价可控」排序。

| # | 收益点 | 机制 | 确定性 | 主要代价 |
| --- | --- | --- | --- | --- |
| R1 | 解决「该搜未搜」 | 请求前判断是否需要联网 | 中高 | 误触发、延迟、成本 |
| R2 | 提升时效性与事实密度 | 实时搜索 + 关键来源下钻 | 高 | 搜索/抓取成本 |
| R3 | **可溯源、可核验** | 统一证据条目，默认带来源/时间 | **最高** | 少量 Token、抓取稳定性 |
| R4 | 暴露来源冲突与不确定性 | 多源对照 + 核验状态标注 | 中高 | 需要证据归一化 |
| R5 | 降低工具轮次与延迟 | 把多轮工具调用压缩为一次预注入 | 中 | 预注入本身有延迟 |
| R6 | **证据复用与记忆复利** | 证据→日记/知识库→RAG/LightMemo 召回 | 中（慢） | 需要沉淀链路与治理 |
| R7 | 多端/多 Agent 一致 | OneRing 时间线 + 共享知识库 | 中低（待设计） | 「事件」定义、来源标记 |
| R8 | 能力与模型解耦 | 小模型/本地模型也能拿到实时事实 | 高 | 同上 |
| R9 | 可审计、可治理 | ToolRecord + 证据 ID + 域名策略 | 中高 | 记录增长、隐私 |
| R10 | 产品差异化与生态复用 | 「每句有出处」；复用现有 105 个插件目录 | 高 | 叙事要克制 |

### 3.1 回答质量收益

**R1 解决「该搜未搜」——概念上最强、实现上最需谨慎。**
VCP 白皮书 §8.1 把「你不记得的东西，怎么知道要去回忆它」当作传统 RAG 的第二个死结。网络检索有完全相同的死结：**模型不知道自己不知道**。当前检索完全依赖模型主动发起工具调用（`docs/FEATURE_MATRIX.md` §9.1 的场景就是「AI 响应含工具调用 → VSearch」），因此漏检率与模型的元认知、工具描述质量、上下文长度强相关；小模型或长对话下漏检更明显。
把「是否需要联网」放到请求构建期判断，等于把这个决策从模型的能力问题变成系统的工程问题。收益是**减少「该查没查」导致的过期/编造回答**。但这条收益依赖触发判断的精度：误触发会把无关问题也带上检索成本与延迟，所以它的收益上限高、下限也低，必须用指标验证。

**R2 提升时效性与事实密度。**
模型知识有截止时间，而 VCP 接入的模型来源多样（newapi 管理、不同厂商、本地模型）。「时效能力与模型解耦」是明确收益：同一套 VCP 后端，换更小/更旧的模型也能拿到当下事实。搜索 + 关键来源下钻还能把「一句话摘要」升级为「有原文片段支撑的事实」，提升事实密度。

**R3 可溯源、可核验——确定性最高的收益。**
这条收益**不依赖回答质量提升**：即使答案不变，带 URL、发布时间、抓取时间、原文片段，用户就能自己核验。现状恰恰相反：`VSearch` 的 `ShowURL` 默认 `false`，官方描述写的是「如果不需要溯源，建议设为 false 以节省 Token」（已核对 manifest）——**溯源与 Token 成本存在直接取舍，而当前默认选择了省 Token**。把「溯源」变成结构化证据的默认属性，是收益最确定、风险最低的一步。

**R4 暴露来源冲突与不确定性。**
多源检索天然会遇到口径冲突（政策不同版本、价格不同时点、媒体互相引用）。证据条目如果保留来源与时间，就能在回答里显式区分「来源事实 / 来源间冲突 / 推断 / 未核实」。这正好对应 Issue #41 提出的「真实、完整、时间线明晰」边界——它不能让回答一定正确，但能让回答**不假装确定**。配合 `JevFactCheck`（需要 evidence）可以在写入日记或交付前做一次断言级核验，形成「检索→生成→核验」闭环。

### 3.2 交互效率与成本收益

**R5 降低工具轮次与延迟。**
当前每次搜索/抓取都是模型的一次工具轮次，`MaxVCPLoopStream` 默认 5（已核对 `docs/CONFIGURATION.md`）。多源搜索 + 来源下钻意味着 2–4 轮工具调用，每轮都要重发上下文、等待模型生成，延迟和 Token 都按轮累加。请求前一次性检索、一次性注入，可以把「搜索 + 2 次抓取」压成一次前置开销。**但这是一把双刃剑**：预注入发生在首 token 之前，若检索耗时 1–2 秒，首字延迟会变差；若误触发，成本反而上升。合理形态应是「短预算同步检索 + 长任务异步」，并带缓存。

**R6 证据复用与记忆复利——长期收益最大。**
一次性检索的收益随对话结束而消失；证据沉淀后，VCP 已有的记忆体系可以持续消费它：
`网络证据 → DailyNote（热记忆）→ KnowledgeBaseManager 索引 → RAGDiary 被动召回 / LightMemo 主动检索`。
一次检索、多次受益，且同一个主题被反复问到时的边际成本趋近于零。VCP 的记忆基础设施（哈希差分、Worker 向量化、LRU、查询缓存）已经成熟（已核对 `docs/MEMORY_SYSTEM.md`），**接上沉淀链路后的复利收益是这台系统里最独特的**。代价是慢：需要积累，且要治理重复、过期、低质证据。

**R7 多端/多 Agent 一致（潜在）。**
`OneRing` 已经维护跨前端统一事实时间线；如果网络采集被定义为「带来源标记的事实事件」，理论上可以进入时间线，让「今天网上发生了什么」跨端可见。但 Issue #41 已经指出、本次核对也确认：**现有材料没有证明网络采集会自动写入 OneRing 或 VCPTimeLine**。因此这是「有空间、未证明」的收益，需要先回答「网络证据算不算事实事件、以什么粒度记录」，不能直接计入。

### 3.3 信任、治理与产品收益

**R8 能力与模型解耦**（见 R2）。对使用本地模型、闭源小模型的用户，收益尤其明显：VCP 后端补上「当下世界」，模型只负责组织语言。

**R9 可审计、可治理。**
证据条目天然带 ID、来源、时间；`VCPToolRecord` 已能记录预处理器内部调用（已核对白皮书 §7.2），因此「这次回答引用了哪些网页、什么时候抓的、哪个源失败」可以回放。对个人用户这是信任，对多 Agent/团队部署这是治理基础。域名白名单/黑名单、抓取频率、Cookie 使用范围也都可以在证据层统一约束。

**R10 产品差异化与生态复用。**
VCP 的定位是「给 AI 一个持续存在的世界」，现有感知主要是时间、天气、日程、记忆；**「当下互联网」是这个世界缺失的一块**。补上后，「每句有出处、带时间」是可对用户表达、可被验证的差异点。同时，这项能力几乎全部复用现有生态——搜索插件、预处理器链、异步通知、记忆、审计、管理面板——**边际建设成本主要是「证据形态 + 编排 + 门控」，而不是重建搜索基础设施**。这是收益/成本比最高的结构性理由。

### 3.4 收益的层次总结

| 层次 | 收益内容 | 兑现速度 | 判断 |
| --- | --- | --- | --- |
| L1 回答层 | 时效、事实密度、可溯源、冲突表达 | 快（改输出形态即可） | 确定性最高，建议先拿 |
| L2 交互层 | 自动按需、少轮次、异步不阻塞 | 中（依赖门控与预算） | 体验收益最大，但误触发风险最高 |
| L3 资产层 | 证据→记忆→复利 | 慢（需要积累与治理） | 长期价值最大，VCP 最独特 |

## 四、收益量化：指标与验证方法（不开发也能开始）

分析阶段的收益判断必须可被证伪。建议在决定开发前，用**只读、不注入**的方式先量基线（不违反「暂不开发」）：

| 维度 | 指标 | 基线采集方式 | 期望方向 |
| --- | --- | --- | --- |
| 漏检 | 「需要联网但未检索」的问题比例 | 抽样 30–50 个时效/事实类问题，人工标注 | 下降 |
| 触发精度 | 触发检索的问题中「确实需要联网」的比例 | 同上 | 越高越好，避免误触发 |
| 时效 | 时效类问题正确率、引用最新来源比例 | 固定题集人工/模型双评 | 上升 |
| 溯源 | 回答带可点击来源的比例、引用-原文一致率、死链率 | 解析回答 + 人工抽查 | 覆盖率上升，死链下降 |
| 效率 | 平均工具轮次、P50/P95 首 token 延迟、每请求 Token | 现有 DebugLog / ToolRecord（只读） | 轮次下降，延迟不显著变差 |
| 复用 | 网络证据写入率、后续 RAG 命中网络证据比例、同主题重复搜索次数 | 记忆侧统计 + 采样 | 写入率/命中率上升，重复搜索下降 |
| 成本 | 搜索 API 成本/千请求、抓取失败率/超时率 | 插件日志统计 | 可控、可降级 |
| 安全 | 注入尝试拦截率、不可信内容标注覆盖率 | 红队样本 | 拦截/标注覆盖上升 |

验证方法（由轻到重）：

1. **离线小样本**：用现有插件手工构造证据条目，针对固定题集比较「有证据/无证据」的回答质量与溯源率。零开发。
2. **影子模式**：线上真实请求时执行检索但不注入，只记录「如果注入会带来什么、耗时多少、成本多少」，用于估算收益与代价。低成本。
3. **小流量 A/B**：只对高精度子集（时效/事实类问题）开启注入，对比正确率、延迟、Token、用户是否点开来源。上线前最后一步。

> 说明：不建议用「搜索次数」或「引用条数」当收益指标——那是成本指标，不是收益指标。收益指标应落在「回答更对/更可核验/更快/更省重复劳动」。

## 五、成本、风险与收益被吞掉的情形

| 风险 | 说明 | 对收益的影响 | 缓解方向（分析层面） |
| --- | --- | --- | --- |
| 延迟 | 预注入在首 token 前，同步检索 30–600s 的插件不可能用于每轮 | 体验收益被延迟抵消 | 短预算同步（秒级）+ 缓存；长任务走异步 |
| Token/成本 | 证据注入 + 每轮搜索 API 费用 | 省轮次的收益可能被证据 Token 吃掉 | 证据裁剪/排序/预算上限；按需触发 |
| 误触发 | 不需要联网的问题也检索 | 成本上升、上下文污染、延迟变差 | 高精度门控 + 可关闭 + 分问题类型 |
| 来源质量 | SEO 污染、内容农场、互相转载 | 证据越多，错误越「像真的」 | 域名权威/白名单、跨源印证、标注来源等级 |
| 时间元数据不可靠 | 发布时间缺失或错误；抓取时间 ≠ 事实发生时间 | 「时间线明晰」承诺落空 | 双时间戳（发布/抓取）+ 缺失即标注未知 |
| **提示注入** | 网页正文是**不可信内容**（ChromeBridge 已明确声明），自动注入会扩大暴露面 | 可能被网页内容操纵工具调用或结论 | 证据只作为数据、与指令分级隔离；沿用不可信内容边界；必要时人工确认高风险动作 |
| 合规/隐私 | robots/ToS/付费墙/版权；UrlFetch 支持 Cookie，抓取登录内容风险更高 | 法务与账号风险 | 域名策略、频率限制、不持久化受限内容、Cookie 范围最小化 |
| 过度自动化 | 「每轮都查」破坏 VCP 现有的稳定前缀缓存与低消耗特性 | 省下的 Token 又被吃回去 | 默认只对高价值子集触发；尊重上下文缓存 |
| 维护 | 搜索 API 改版/限额/失败 | 收益不稳定 | 多源可切换 + 失败降级 |
| 收益高估 | 把「可核验」说成「一定真」、把多源说成「全网完整」 | 用户预期落空、信任反噬 | 明确边界与覆盖范围（见第六节） |

**收益会被吞掉的三种典型情形**（判断是否值得做的关键）：

1. 触发不准：误触发多 → 成本与延迟上升，质量收益不明显；
2. 证据不归一：各插件还是各说各话 → 只有「更多文字」，没有「更可核验」；
3. 不沉淀：检索完就丢 → 只有一次性收益，拿不到记忆复利。

## 六、收益边界：「真实、完整、时间线明晰」能兑现到什么程度

Issue #41 把目标表述为「真实、完整、时间线明晰」。逐项拆开，收益边界才清楚：

| 目标 | 检索链能做的 | 不能保证的 | 可交付的表达 |
| --- | --- | --- | --- |
| 真实 | 提高可核验性：给来源、给原文片段、给核验状态 | 不能保证来源本身为真，也不能保证模型正确引用 | 「来源事实 / 来源间冲突 / 推断 / 未核实」四分类 |
| 完整 | 多源搜索 + 下钻提高覆盖，减少单一来源偏见 | 不能保证「全网」；登录页、付费墙、动态页、区域限制都有盲区 | 说明覆盖范围与已知盲区，不承诺无遗漏 |
| 时间线明晰 | 记录抓取时间；来源提供发布时间时一并保留 | 发布时间常缺失/错误；「发布」不等于「事实发生」 | 发布/抓取双时间戳 + 时效提示 |

这条边界不是收益的否定，而是**把收益从「不可验证的承诺」换成「可验证的属性」**：从「我能给你全网真相」换成「我给你的每句话都能点开看、能看出是什么时候的、冲突在哪」。后者才是可交付、可测试、可长期维护的收益。

## 七、如果要做：收益兑现顺序（分析建议，不是开发排期）

按「收益确定性 ÷ 成本与风险」排序，结论如下：

| 顺序 | 做什么 | 能拿到的收益 | 风险 | 判断 |
| --- | --- | --- | --- | --- |
| 1 | 统一「证据条目」形态，搜索结果默认带来源/时间，注入时按预算裁剪 | R3 溯源、R4 冲突表达（确定性最高） | 低 | **先做这个，收益立刻可见且不改变调用方式** |
| 2 | 对高精度子集（时效/事实类）做请求前按需检索，带预算、缓存、失败降级 | R1 该搜未搜、R5 少轮次 | 中高（误触发/延迟） | 体验收益最大，但必须先有第 4 节的指标与门控 |
| 3 | 证据 → DailyNote/知识库 → RAG/LightMemo 召回 | R6 记忆复利 | 中（治理成本） | 长期价值最大，建议在前两步稳定后做 |
| 4 | 深度研究异步化（提交任务 + 完成通知 + 后续可取回） | 长任务不阻塞、体验完整 | 中（插件形态改造） | 协议已具备，收益明确但非最紧急 |
| 不建议先做 | 自建爬虫/全网索引/「证据库」大工程 | 覆盖略增 | 高（成本、合规、维护） | 现有搜索源已足够，投入产出比低 |

**如果只做一件事**：做第 1 项。它不改变现有调用方式、风险最低，却能把「AI 回答」升级为「可点开核验的回答」，这是当前收益/成本比最高的一步，也是后续证据沉淀与自动检索的数据基础。

## 八、结论

1. **收益成立。** 分为三层：L1 回答质量与可溯源（快、确定）、L2 自动按需与效率（大、但依赖门控）、L3 证据记忆复利（慢、最独特）。
2. **最大收益不来自「更多搜索源」，而来自「证据化 + 记忆化」。** VCP 的搜索/抓取零件已经足够；真正缺的是统一证据形态与沉淀链路。
3. **最值得先拿的是「可溯源」。** 它不依赖回答质量提升、风险低、用户可感知，且是后续一切证据工作的基础。
4. **最需要谨慎的是「自动按需」。** 它解决 VCP 自己指出的「该搜未搜」死结，收益上限最高，但误触发、延迟、提示注入三项风险也最高，必须用指标和门控先验证。
5. **不应承诺「全网、无遗漏」。** 可交付的目标是「可核验、可区分冲突、可看出时间」，而不是「一定真、一定全」。
6. **建议的决策路径**：先按第 4 节以只读/影子方式验证收益与代价（不违反「暂不开发」），再决定是否进入第 1、2 项的开发。
